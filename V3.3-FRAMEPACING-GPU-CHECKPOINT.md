# V3.3 frame-pacing and GPU checkpoint

Base checkpoint: `v3.2-known-good-20260826` at `aa6fc1a8b6`, validated by
GitHub Actions run 32928134788 on Windows Server 2022/MSVC.

Development branch: `v3.3-framepacing-gpu`

The first V3.3 checkpoint at `cb4a3be7f2` passed the full Windows Server
2022/MSVC build in GitHub Actions run
[32935143686](https://github.com/JesusIsGod316/openmwcustom/actions/runs/32935143686).

## Source audit conclusions

- Current OpenMW renders every enabled shadow cascade every frame. The V3
  shadow stream measures CPU receiver/caster cull time per cascade, while the
  existing OSG offline statistics path supplies driver-managed asynchronous GPU
  timing and render statistics when `OPENMW_OSG_STATS_LIST=times;resource`.
- Groundcover has its own `Mask_Groundcover` and is not added to the current
  outdoor shadow-casting mask. The first V3.3 change therefore does not reduce
  grass density, grass distance, or global shadow resolution.
- Predictive exterior preloading already uses player velocity, but the complete
  eligible outer ring can submit new speculative cell jobs in one frame. Actual
  cell-grid activation and required terrain synchronization are separate and
  remain synchronous.
- OSG 3.6 merges its complete ready DatabasePager queue during
  `updateTraversal()`. Its public pager API exposes queue sizes but not a
  bounded, millisecond-budgeted merge call. The first V3.3 checkpoint therefore
  measures update traversal explicitly and controls speculative work admission;
  it does not claim to implement a result-integration budget inside OSG.
- Existing DXGI/WDDM telemetry measures OpenMW's process-local local-memory
  budget. It does not expose total NVIDIA adapter usage.
- The V3.2 transition result remains valid: retained cheap static render state
  did not remove the controller-construction bottleneck. V3.3 does not broaden
  hibernation to actors, doors, scripts, or animated ownership.

## Measured V3.2 baselines

Repeatable Project Cyrodiil outdoor traversal:

- median 22.01 ms; p95 30.18 ms; p99 36.83 ms; p99.5 47.82 ms;
- 22.75% of frames above 25 ms, 2.11% above 33.3 ms, 0.44% above
  50 ms, and 0.16% above 100 ms;
- four obvious cell-boundary frames at approximately 629.8, 487.0, 260.9,
  and 222.3 ms.

The 630 ms and 487 ms examples leave roughly 420 ms and 374 ms respectively
outside the existing engine-stage and paging timers. The expanded frame stream
is specifically designed to divide this previous `other_ms` bucket among OSG
event traversal, OSG update/pager integration, rendering traversal, Lua wait,
frame limiting, viewer advance, and the remaining uninstrumented tail.

Heavy outdoor rendering baseline:

- median 23.57 ms; p95 30.45 ms; p99 37.46 ms;
- 30.47% above 25 ms, 2.04% above 33.3 ms, 0.59% above 50 ms,
  and 0.12% above 100 ms.

Current shadow instrumentation reports approximately 11.51 ms average tracked
CPU-side shadow work: 6.49 ms receiver traversal and 4.78 ms caster traversal,
with cascades 0/1/2 at about 0.74/1.35/2.69 ms. These are CPU cull costs, not
GPU time. This makes conservative far-cascade reuse a measured target while
leaving near-player quality unchanged.

Object paging is the more credible traversal target than terrain: active-grid
object chunks total roughly 738 ms, distant chunks 386 ms, groundcover 171 ms,
and terrain only 40 ms after startup. Scene-template misses total roughly 6.62 s
across the render run with a 137.7 ms worst miss, but those calls may execute on
workers; the new common-frame streams are needed before changing that path.

Process-local DXGI usage peaked near 5.98 GB in City and 6.15 GB in Render,
while adapter-wide monitoring reached roughly 7.5 GB on the 8 GB card. NVML is
therefore observational in this checkpoint and is not used to drive residency
policy.

## First V3.3 runtime experiments

All new behavior is off by default and independently selectable in the same
binary.

### Predictive speculative-preload admission budget

`[Cells] v3.3 speculative preload budget = 0` preserves the existing unlimited
speculative scheduling behavior. A positive value limits only new predictive
outer-ring cell jobs per frame. Already-preloaded candidates are refreshed, and
remaining candidates age naturally into the next frame. Candidates are sorted
by predicted-position distance with a smaller current-position component.
Required cell loading is unchanged.

The initial launcher experiment uses a budget of two new speculative cells per
frame. Streaming telemetry records attempted new, refreshed, and deferred
candidate counts. This smooths the arrival rate of optional worker jobs; it is
not the eventual work-class/time-budgeted main-thread integration scheduler.

### Conservative far-cascade reuse

`[Shadows] v3.3 far cascade update interval = 1` preserves full per-frame
cascade updates. The initial experiment sets the interval to two and applies
only to the farthest cascade.

Reuse requires:

- an existing valid shadow texture and matching cascade/texture slot;
- update age below the configured interval;
- projected frustum-corner drift no greater than the configured texel guard;
- actor and player shadow casting to be disabled.

On reuse, both the old texture and its matching view/projection matrices are
retained. Near cascades always update. The shadow CSV reports updated/reused
cascade counts and maximum accepted texel drift.

### Profiling and VRAM

- City profiles now collect frame, hitch, cell event, paging, resource,
  insertion, workqueue, render, shadow, OSG, and GPU-memory streams with common
  frame identifiers.
- Cell-grid changes emit an explicit event for spike correlation.
- A 300-frame summary stream reports mean, median, p95, p99, p99.5, worst
  frame, and counts above 25, 33.3, 50, and 100 ms.
- NVML is loaded dynamically from `nvml.dll`. When available, the GPU-memory CSV
  adds total adapter used/free/total memory. Missing NVML is a normal fallback
  and does not disable DXGI process-budget telemetry.
- No synchronous OpenGL timer query was added. The existing OSG GPU statistics
  collection remains the GPU timing path.

## First V3.3 A/B findings

Comparable active-window City results:

| Run | Median | p95 | p99 | >25 ms | >33.3 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| Baseline | 22.47 ms | 29.23 ms | 33.97 ms | 22.08% | 1.29% |
| Preload budget | 22.72 ms | 29.84 ms | 36.18 ms | 25.46% | 2.13% |
| Combined | 22.64 ms | 29.86 ms | 35.99 ms | 27.14% | 2.04% |

Baseline p99.5 was 46.95 ms, with 0.48% of frames above 50 ms and
0.085% above 100 ms.

The preload budget deferred candidates only about five times across roughly
6,300 frames. The far-shadow experiment reused zero cascades because actor and
player shadows were enabled, so the latter two results do not measure active
optimizations and are treated as run-to-run variance.

Four representative baseline cell-boundary hitches averaged approximately
307 ms total, including 115 ms in synchronous world update and 144 ms waiting
in `mLuaWorker->finishUpdate()`. Individual Lua-worker waits ranged from about
51 to 308 ms. The formerly large unexplained frame-tail bucket is therefore
largely accounted for by world activation and Lua-worker completion, not OSG
event/update traversal or unexplained render-driver time.

The existing Lua telemetry is sufficient for the next diagnostic pass:

- `v3-lua-update.csv` divides the worker update into object-list, autostart,
  prune, stats, event-finalization, timer, event-handler, callback, engine-event,
  local/global update, and tracker phases;
- `v3-luasync.csv` profiles the main-thread synchronized Lua update;
- `v3-lua-actions.csv` profiles queued and teleport actions.

City launcher profiles now enable all three streams. The synchronization
barrier and execution order are unchanged. `ObjectLists::update()` already
rebuilds only categories marked changed by object add/remove operations, so the
next measurement should identify whether list copying or a later Lua phase is
actually responsible before any incremental/batching change is attempted.

Comparable active-window Render results:

| Run | Frame median | Frame p95 | Frame p99 | Async GPU median | Shadow CPU avg |
| --- | ---: | ---: | ---: | ---: | ---: |
| Baseline | 22.89 ms | 30.42 ms | 35.88 ms | 22.30 ms | 11.00 ms |
| Far-shadow option | 22.73 ms | 30.25 ms | 37.07 ms | 21.96 ms | 10.97 ms |

All Render runs updated all three cascades on every frame and reused none.
Their small differences are normal variance. The approximately 22.9 ms wall

outdoor rendering is strongly GPU-bound. A separate roughly 454 ms world-change
frame contained about 163 ms of world work and 206 ms of Lua-worker wait,

The baseline asynchronous GPU draw p95 was 27.69 ms.

NVML measured a total RTX 5050 capacity of 8,151 MB and approximately
7.39--7.41 GB peak adapter occupancy in Render, about 91%. City peaks were
approximately 7,348 MB baseline, 7,408 MB preload, and 7,310 MB combined while
process-local DXGI usage remained about 5.8--6.0 GB. Both adapter-wide NVML and
process-local DXGI metrics remain permanent diagnostics.

## Revised engineering order

1. Use the newly enabled City Lua streams to identify the late worker phase and
   correlate separate `lua_sync_ms` spikes.
2. Continue isolating synchronous world cell-activation work.
3. Replace the current far-cascade experiment with an actor/player-compatible
   design; do not disable those shadows implicitly.
4. Keep dual NVML/DXGI VRAM telemetry.
5. Deprioritize speculative budget-two tuning until the dominant world/Lua
   costs are understood.

Starting the Lua worker earlier is only a candidate after ownership review. It
currently begins after world/GUI mutation, OSG event and update traversal, and
focus update, then overlaps rendering. The worker reads world time, world-model
objects, events, and active script state and publishes delayed work consumed by
the next synchronized update, so moving it across any of those producers needs
explicit dependency proof rather than merely moving `allowUpdate()`.

## Shadow redesign boundary

The current shadow technique applies one `CastsShadowTraversalMask` to every
cascade and owns one depth texture per cascade. Actor and player nodes already
have distinct traversal-mask bits, so a future experiment can explicitly omit
those dynamic casters from only the far cascade while retaining their near and
middle shadows. That is a visible distance-quality policy, however, and must be
an opt-in setting rather than an implicit consequence of enabling reuse.

True far-cascade reuse with dynamic actor/player shadows at the same distance
cannot safely update those actors into the cached depth texture: departed or
moved actors would leave stale depth behind. The architecture-safe form needs a
separate static far depth layer plus a dynamic far layer sampled together by the
receiving shader. That changes texture allocation, global texture-unit
reservation, RTT traversal, uniforms, and shaders, and should be prototyped as
an independent experiment with visual checks and OSG GPU timing. With adapter
occupancy already around 91%, its additional residency must also be measured.
