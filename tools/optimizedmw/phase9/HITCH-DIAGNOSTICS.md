## Engine capture

Run `START-OptimizedMW-Test.bat` normally and choose **1 = Diagnose CONTROL**. Accept the Windows administrator prompt for the recorder; the game starts automatically after recording is ready. Use the same outdoor save, heavy fixed view and route, and quit normally. Wait for packaging, then upload the single ZIP selected in Explorer. It includes the unchanged engine/system archives and final qualification when available. For engine-only Deep diagnostics, choose **C = Custom**, combination 0, Deep, original I/O, then N at the Windows-trace prompt. Earlier numbered mode 3 remains inside **A = Earlier Phase 9 modes**. The ZIP contains the raw timeline, writer/trace loss records, full Lua update and controller/script setup writers, and frame pacing analysis. `HITCH-PHASE-TOTALS.csv` summarizes retained phase exposure; `HITCH-REMAINING-SCOPES.csv` shows the largest residual intervals. The raw timeline retains parent IDs, native Windows thread IDs, logical asset paths and timestamps for detailed reconstruction.

Trace modes use a pre-touched 524,288-row arena. The extended row stores one causal link and four named integer metrics; this larger diagnostic arena is allocated only when the trace is armed. The capture status records the selected capacity. Normal mode 1 does not allocate it. The resource catalog remains 131,072 entries. Rows below 0.25 ms can be filtered, but their time is still included in the parent's child total. Explicit dependency events, hash summaries and stream totals are retained even when short. Causal links are independent of parent nesting and never imply that worker wall time should be subtracted from a main-thread wait. Arena overflow, writer drops, missing completion, incoherent parents or missing requested channels invalidate the affected capture. The report accepts the earlier 15-column format and 131,072/262,144-row capacities for historical captures, as well as the new 24-column format. HITCH-DEPENDENCIES.json preserves retained causal scopes; HITCH-DIAGNOSTIC-COST.csv separates diagnostic phase exposure. Lua allocation deltas are inclusive successful logical realloc changes, not OS memory allocations or retained script memory; calls without ScriptId are outside these per-call counters. Stream read totals are logical reads, not disk traffic, and are published at stream destruction. Successful opens without totals explicitly have unavailable aggregate coverage. Resource catalog all-call wall totals exclude fixed scope/counter bookkeeping and are not OS CPU totals.

Inclusive nested scopes must not be added together. Phase totals cover retained spans; different threads overlap. `unattributed_ms` means time outside instrumented direct children, which can include known leaf operations and instrumentation overhead. Windows GetThreadTimes is coarse, and short CPU deltas can exceed the corresponding wall interval. These values do not establish precise scheduler wait time.

## Automatic and advanced Windows system trace

Choices **1 = Diagnose CONTROL** and **4 = Diagnose ALL** coordinate Windows recording automatically. The recorder alone requests elevation; the game retains normal permissions. The default limit is **600 seconds from recorder start**. The launcher waits for the exact recorder ready state, preserves capture identity, stops cooperatively after game exit or launch failure, waits for saving/qualification, and verifies the combined upload ZIP. Settings/environment restoration and raw evidence rules are unchanged. Failed elevation/readiness prevents this advertised system-trace run from silently becoming an engine-only run. Duration/space/loss/unknown coverage remains explicit. Normal choices **2** and **3** start no recorder.

For scripted Deep tracing, use `START-OptimizedMW-Test.bat -HitchMask 0 -TraceLevel Deep -SystemTrace`. Add `-SystemTraceDurationSeconds 900` for a longer recording; range 30-1800 seconds. The manual recorder remains available for advanced use with the following steps:

1. Right-click `START-OptimizedMW-SystemTrace.bat` and choose **Run as administrator**. Wait for the recording-started message and keep that window open.
2. Start `START-OptimizedMW-Test.bat` normally in a separate window and choose **A**, then earlier mode **3**. Use the same outdoor save, about 45 seconds in the fixed heavy view, then the same 2–3 minute route.
3. Quit the game normally. The recorder automatically saves after observing that exact game process exit. Its default time limit is **360 seconds from recorder start**, so launch promptly. Enter stops early. For a longer run, start the recorder with `-DurationSeconds 600`; the supported range is 30–1800 seconds.
4. Let both windows finish saving/reporting. Share the mode 3 ZIP beside the launcher and the matching ZIP under `SystemTrace`. Also share the file beside the engine ZIP named `<engine.zip>.system-qualification.json` when present. The final qualification can finish after the system ZIP; this companion file supplies its completed result without recompressing the ETL. Keep the raw capture directory.

File mode writes the full run sequentially rather than overwriting early events in circular memory. At least 10 GiB must be free at start; the recorder also reserves merge/save space based on current temporary trace size. Actual retained scheduling bounds, anchor gaps and loss counts determine coverage. The default duration, disk guard or manual stop can still truncate a game run. `-Mode Memory` remains an explicit circular control and can overwrite early evidence.

A normal Windows launch includes the game and a separate `openmw.exe --crash-monitor` helper. The recorder identifies the helper from its exact command-line grammar, records its PID, birth time and parent separately, and counts only engine instances for automatic stopping. It keeps crash reporting enabled. If two actual engine instances are observed, it saves the trace with explicit ambiguity instead of cancelling the evidence.

The helper uses a unique WPR instance and only stops/cancels that instance. It records exact executable path/hash, native PID and process creation time. A GUID and recorder lifetime are copied into the engine profile; after final engine ZIP creation, a separate atomic binding records that ZIP's hash and bytes. Stale recorder state, a different binary/process, and replaced ZIPs cannot silently qualify. A saving recorder produces a pending result without holding the game launcher open. Preliminary ETL-only results and final engine-bound results have separate names. Raw captures remain available when qualification fails. The game runs with its normal permissions.

The qualifier reports observed DxgKrnl event kinds and explicitly flags zero GPU events. Provider availability does not prove DMA packet decoding, GPU queue ownership, shader compilation, or private driver internals. Full-range scheduling qualification means retained timestamps bracket the calibrated engine recorder lifetime with no reported loss; it does not prove absence of every interior event hole. An unavailable or partial channel stays unavailable or partial in the report.

`p9-hitch-spans.csv.clock-map.txt` supplies process ID, native thread ID convention, QPC frequency, paired steady-clock/QPC brackets at start/end, UTC anchors and normal completion. Align a span's steady timestamp with QPC using these brackets and check drift/uncertainty; do not assume that epoch milliseconds or independent frame IDs imply exact alignment. Selected GL rows use the same steady clock and include their native thread ID.

In Windows Performance Analyzer, narrow the ETL to the matching process/thread and calibrated hitch interval. CPU Usage (Precise) separates running, ready and blocked intervals and identifies the thread that made a blocked thread runnable. Sampled stacks, disk/file I/O, hard faults and DPC/interrupt tables test alternative causes. GPU events can identify queue activity and overlapping execution where the driver emits them. Match exact `openmw.exe` and `openmw.pdb`; matching engine symbols remain in the local build directory recorded in `Validation/BUILD-AND-TEST-STATE.json`. WPA is not installed by the game package.

NVIDIA private driver implementation and missing private symbols remain partly opaque. A long GL call alone does not prove shader compilation, GPU execution, residency eviction, or an OS scheduling delay. ETW scheduling and GPU events can narrow those alternatives, but only the captured evidence can justify a diagnosis. WPR profile validation is automated; actual elevated recording and runtime hitch diagnosis require a user capture.
